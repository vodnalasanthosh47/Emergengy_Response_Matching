# Data Format

The single reference for **how requests and resources are stored**: their keys, the
record around them, the index attributes, and the domain documents inside. The Java
services (Request, Resource, Matching) must write data exactly in this format; the
coordinator rejects keys and indexes that break the rules.

- Format version: **2026-11-19** (requests sharded by request ID, resources by geohash
  cell). Data in the earlier `{collection}:{homeCell}:{uuid}` format is no longer
  accepted and was deleted on 2026-11-19.
- Contract: `contracts/openapi/coordinator-api.yaml` (what the services call).
- Decision and reasoning: ADR 0006 (sharding), ADR 0009 (replication, write fencing).
- How a record sits inside MongoDB on a storage node: `docs/storage-schema.md`.

Every example value below is real: the geohashes were computed from the coordinates
shown, the shards with `crc32(token) mod 3`, and every request was run against the
Compose stack.

---

## 1. Three layers

```
Client JSON (public API)          what POST /requests returns       — owned by each service
   │  service builds key + record
   ▼
Storage record (coordinator API)  { key, value, indexes, version, updatedAt }
   │  coordinator routes by key, storage node stores
   ▼
MongoDB document (storage node)   { _id, value, indexes, version, updatedAt, deleted }
```

- **`value`** is the domain document (section 5 and 6). Storage never reads it.
- **`indexes`** are the few attributes storage can search on (section 4).
- **`version`** and **`updatedAt`** are managed by storage (section 3).

---

## 2. Keys

The key decides the shard, so it must be built exactly as below.

| Collection | Key | Shard | Example | Shard of example |
|---|---|---|---|---|
| request | `request:{requestId}` | `crc32(requestId) mod 3` | `request:f3b1c2e4-0d1e-4a5b-9c8d-7e6f5a4b3c2d` | 0 |
| resource | `resource:{geoCell}:{uuid}` | `crc32(geoCell) mod 3` | `resource:tdr1v9:8a7c3e0e-4c1d-4b9a-9d55-0d3c2f1a9b77` | 1 (cell `tdr1v9`) |

### 2.1 Parts

| Part | Format | Notes |
|---|---|---|
| `requestId` | UUID v4, lower case (`f3b1c2e4-0d1e-4a5b-9c8d-7e6f5a4b3c2d`) | Generated by the Request Service. Any `[A-Za-z0-9_-]+` is accepted. |
| `uuid` (resource) | UUID v4, lower case | Generated by the Resource Service. Any `[A-Za-z0-9_-]+` is accepted. |
| `geoCell` | Geohash of the resource's location, **precision 6**, lower case | Alphabet `0123456789bcdefghjkmnpqrstuvwxyz` (no `a i l o`). Precision is `GEOHASH_PRECISION` (default 6, ≈ 0.61 km × 1.19 km here), the same in every service. It must never change once data exists. |

Whole key: letters, digits, `:`, `_`, `-`; 1–256 characters; no `/`.

### 2.2 Client IDs ↔ storage keys

| Client sees | Storage key | Conversion |
|---|---|---|
| `requestId` = `f3b1c2e4-…` | `request:f3b1c2e4-…` | prefix `request:` |
| `resourceId` = `res_tdr1v9_8a7c3e0e-…` | `resource:tdr1v9:8a7c3e0e-…` | `res_{cell}_{uuid}` ↔ `resource:{cell}:{uuid}` |

A geohash contains no `_` and a UUID contains only `-`, so splitting `resourceId` on
the first two `_` is unambiguous:

```text
toKey("res_tdr1v9_8a7c...")       = "resource:" + cell + ":" + uuid   where [_, cell, uuid] = split("_", 3)
toResourceId("resource:tdr1v9:8a7c...") = "res_" + cell + "_" + uuid  where [_, cell, uuid] = split(":", 3)
```

### 2.3 Rules

- A resource's cell is fixed by its key. **Moving a resource = re-keying it**: delete
  the old key, create a new one in the new cell (spec §3.5).
- Requests are not keyed by location: a request in cell `tdr1v9` can be on any shard.
  In the failover test, 60 requests from one cell landed on all 3 shards.
- Rejected with `400 INVALID_REQUEST`:

| Key | Why |
|---|---|
| `request:tdr1v9:f3b1…` | request keys have no cell |
| `request:` | empty request ID |
| `resource:8a7c…` | missing cell |
| `resource:smoke1:8a7c…` | `o` is not a geohash character |
| `resource:TDR1V9:8a7c…` | geohashes are lower case |
| `resource:tdr1v9:8a7c…:x` | extra segment |
| `request/abc` | `/` not allowed |

> **Note on the spec's example:** PROJECT_SPEC §3.2 shows `"geoCell": "tdr1yz"` for
> location 12.9716, 77.5946. That is illustrative only: the real precision-6 geohash
> of that point is **`tdr1v9`** (checked against the reference value
> `57.64911, 10.40744 → u4pruydqqvj`). Unit tests in the Java services should expect
> `tdr1v9`.

## 3. The record

### 3.1 Writing: `PUT /v1/data/{key}`

```json
{
  "value":   { "...": "domain document, a JSON object" },
  "indexes": { "collection": "resource", "type": "WATER", "status": "AVAILABLE", "geoCell": "tdr1v9" },
  "expectedVersion": 1
}
```

| Field | Required | Meaning |
|---|---|---|
| `value` | yes | The full domain document (a JSON object). Stored and returned exactly as written; integers stay integers. Keys must not start with `$`. |
| `indexes` | yes | Flat string attributes for queries; see section 4. |
| `expectedVersion` | no | Optimistic concurrency, below. Unknown fields (e.g. the misspelling `expectedVerison`) are rejected with `400`, so a claim can never silently turn unconditional. Field names are matched case-insensitively, so `expectedversion` still means `expectedVersion`. |

| `expectedVersion` | key missing | key at version n | key at another version |
|---|---|---|---|
| omitted | create → `201` | replace → `200` | replace → `200` |
| `0` ("must not exist") | create → `201` | `409` | `409` |
| `n ≥ 1` ("must be at n") | `412` | replace → `200` | `409` |

**Every claim and every status change must pass `expectedVersion`.** On `409` re-read
and decide again.

### 3.2 Reading: the `Record`

```json
{
  "key": "resource:tdr1v9:8a7c3e0e-4c1d-4b9a-9d55-0d3c2f1a9b77",
  "value": { "...": "exactly as written" },
  "indexes": { "collection": "resource", "type": "WATER", "status": "AVAILABLE", "geoCell": "tdr1v9" },
  "version": 2,
  "updatedAt": "2026-11-19T10:15:02.481Z"
}
```

| Field | Set by | Meaning |
|---|---|---|
| `version` | storage | 1 on create, +1 on every successful write. Deleting and re-creating a key keeps counting up, so a stale version can never match the new record. |
| `updatedAt` | storage | Time of the last write (UTC, milliseconds). Used for replication and recovery. |

**`version` lives in the record, not in `value`.** The public API shows it (spec
§3.2) by copying `record.version` into the response. Do not store it inside `value`,
where it would go stale. Likewise, `value.createdAt` / `value.updatedAt` are the
service's own timestamps (ISO-8601 strings), separate from the record's `updatedAt`.

## 4. Index attributes

Indexes are what `POST /v1/query` can match on (exact string equality). They copy
fields out of `value`; **a write that changes one of these fields in `value` must
change it in `indexes` in the same write**.

| Attribute | request | resource | Value |
|---|---|---|---|
| `collection` | **required**, `request` | **required**, `resource` | must match the key's collection |
| `type` | required | required | `WATER` \| `FOOD` \| `MEDICINE` \| `TRANSPORT` \| `SHELTER` |
| `status` | required | required | request or resource status (sections 5.2, 6.2) |
| `geoCell` | required | **required, = key's cell** | precision-6 geohash of the location |

- Enforced by the coordinator (`400`): `collection` must match the key, and a
  resource's `geoCell` must equal the cell in its key. The coordinator sends a geo
  query only to the shards owning the queried cells, so a resource indexed under
  another cell would never be found.
- "Required" without bold is the services' convention, needed for the queries in
  section 7; storage accepts its absence.
- Names: letters, digits, `_` (max 64). Values: strings. Only `collection`, `geoCell`,
  `type` and `status` have MongoDB indexes; other attributes work but scan.
- A request's `geoCell` is searchable data only; it does not decide its shard.

## 5. Request

### 5.1 Stored record

```json
{
  "key": "request:f3b1c2e4-0d1e-4a5b-9c8d-7e6f5a4b3c2d",
  "value": {
    "requestId": "f3b1c2e4-0d1e-4a5b-9c8d-7e6f5a4b3c2d",
    "type": "WATER",
    "location": { "lat": 12.9716, "lng": 77.5946 },
    "geoCell": "tdr1v9",
    "status": "PENDING",
    "requester": { "name": "Ravi Kumar", "contact": "+91-90000-00000" },
    "details": { "quantity": 20, "unit": "L" },
    "assignedResourceId": null,
    "createdAt": "2026-11-19T10:15:00Z",
    "updatedAt": "2026-11-19T10:15:00Z"
  },
  "indexes": { "collection": "request", "type": "WATER", "status": "PENDING", "geoCell": "tdr1v9" },
  "version": 1,
  "updatedAt": "2026-11-19T10:15:00.123Z"
}
```

| `value` field | Type | Notes |
|---|---|---|
| `requestId` | string (UUID) | Same as in the key. |
| `type` | enum | `WATER` \| `FOOD` \| `MEDICINE` \| `TRANSPORT` \| `SHELTER` |
| `location` | `{lat, lng}` numbers | WGS84 degrees. |
| `geoCell` | string | Computed by the service from `location`; clients never send it. |
| `status` | enum | Section 5.2. |
| `requester` | `{name, contact}` | Optional. |
| `details` | object | Shape by `type`, section 5.3. |
| `assignedResourceId` | string \| null | Client form `res_{cell}_{uuid}` once `MATCHED`. |
| `createdAt`, `updatedAt` | ISO-8601 string | Set by the service. |

### 5.2 Request status

```
PENDING ──► MATCHED ──► IN_PROGRESS ──► FULFILLED
   │  ▲         │
   │  └ UNMATCHED (no candidate yet; may be retried)
   └──► CANCELLED  (allowed from PENDING / UNMATCHED / MATCHED)
```

Illegal transitions are refused by the Request Service (`409`). Each transition is one
conditional write updating `value.status`, `value.updatedAt` **and** `indexes.status`.

### 5.3 `details` by type

| type | details | Amount compared with resource capacity |
|---|---|---|
| WATER | `{ "quantity": number > 0, "unit": "L" }` | `quantity` |
| FOOD | `{ "quantity": int > 0, "unit": "MEALS" }` | `quantity` |
| MEDICINE | `{ "name": string, "quantity": int > 0 }` | `quantity` (and `name` must equal the resource's) |
| TRANSPORT | `{ "people": int > 0, "start"?: {lat, lng}, "destination"?: {lat, lng} }` | `people` |
| SHELTER | `{ "people": int > 0 }` | `people` |

## 6. Resource

### 6.1 Stored record

```json
{
  "key": "resource:tdr1v9:8a7c3e0e-4c1d-4b9a-9d55-0d3c2f1a9b77",
  "value": {
    "resourceId": "res_tdr1v9_8a7c3e0e-4c1d-4b9a-9d55-0d3c2f1a9b77",
    "type": "WATER",
    "provider": { "name": "Akshaya NGO", "kind": "NGO", "contact": "+91-80000-00000" },
    "location": { "lat": 12.97, "lng": 77.59 },
    "geoCell": "tdr1v9",
    "capacity": { "total": 500, "remaining": 500, "unit": "L" },
    "details": {},
    "status": "AVAILABLE",
    "createdAt": "2026-11-19T10:00:00Z",
    "updatedAt": "2026-11-19T10:00:00Z"
  },
  "indexes": { "collection": "resource", "type": "WATER", "status": "AVAILABLE", "geoCell": "tdr1v9" },
  "version": 1,
  "updatedAt": "2026-11-19T10:00:00.456Z"
}
```

| `value` field | Type | Notes |
|---|---|---|
| `resourceId` | string | `res_{geoCell}_{uuid}`, from the key. |
| `type` | enum | Same categories as requests (that is what matching joins on). |
| `provider` | `{name, kind, contact}` | `kind`: `VOLUNTEER` \| `NGO` \| `GOVT` \| `INDIVIDUAL` \| `OTHER`. A provider is not a type. |
| `location`, `geoCell` | as for requests | `geoCell` **must equal the key's cell and `indexes.geoCell`**. |
| `capacity` | `{total, remaining, unit}` | `remaining` decreases on each claim. |
| `details` | object | MEDICINE: `{ "name": string }`; others `{}`. |
| `status` | enum | Section 6.2. |
| `createdAt`, `updatedAt` | ISO-8601 string | Set by the service. |

### 6.2 Resource status

`AVAILABLE` | `DEPLETED` (remaining reached 0) | `OFFLINE` (withdrawn by the provider).
A resource can serve a request when `status == AVAILABLE` and
`capacity.remaining >= amount` (section 5.3). One request is served by one resource.

## 7. Operations as storage calls

`$C` is the coordinator (`http://coordinator:8080` inside Compose,
`http://localhost:9090` with `make up-dev`).

**Create a request** (create-only, so a retried POST cannot overwrite):

```bash
curl -X PUT "$C/v1/data/request:f3b1c2e4-0d1e-4a5b-9c8d-7e6f5a4b3c2d" -H 'Content-Type: application/json' -d '{
  "value": { "requestId": "f3b1c2e4-0d1e-4a5b-9c8d-7e6f5a4b3c2d", "type": "WATER",
             "location": {"lat": 12.9716, "lng": 77.5946}, "geoCell": "tdr1v9", "status": "PENDING",
             "details": {"quantity": 20, "unit": "L"}, "assignedResourceId": null,
             "createdAt": "2026-11-19T10:15:00Z", "updatedAt": "2026-11-19T10:15:00Z" },
  "indexes": { "collection": "request", "type": "WATER", "status": "PENDING", "geoCell": "tdr1v9" },
  "expectedVersion": 0 }'
# → 201, record with "version": 1
```

**Get a request:** `GET $C/v1/data/request:{requestId}` → `200` / `404`.

**Register a resource:**

```bash
curl -X PUT "$C/v1/data/resource:tdr1v9:8a7c3e0e-4c1d-4b9a-9d55-0d3c2f1a9b77" -H 'Content-Type: application/json' -d '{
  "value": { "resourceId": "res_tdr1v9_8a7c3e0e-4c1d-4b9a-9d55-0d3c2f1a9b77", "type": "WATER",
             "provider": {"name": "Akshaya NGO", "kind": "NGO", "contact": "+91-80000-00000"},
             "location": {"lat": 12.97, "lng": 77.59}, "geoCell": "tdr1v9",
             "capacity": {"total": 500, "remaining": 500, "unit": "L"}, "details": {}, "status": "AVAILABLE",
             "createdAt": "2026-11-19T10:00:00Z", "updatedAt": "2026-11-19T10:00:00Z" },
  "indexes": { "collection": "resource", "type": "WATER", "status": "AVAILABLE", "geoCell": "tdr1v9" },
  "expectedVersion": 0 }'
# → 201, "version": 1
```

**Find candidates near a request** (its cell + 8 neighbours):

```bash
curl -X POST "$C/v1/query" -H 'Content-Type: application/json' -d '{
  "collection": "resource",
  "geoCells": ["tdr1v6","tdr1vd","tdr1vf","tdr1v3","tdr1v9","tdr1vc","tdr1v2","tdr1v8","tdr1vb"],
  "match": { "type": "WATER", "status": "AVAILABLE" },
  "limit": 50 }'
# → 200 { "records": [ ... ] }, sorted by key
```

The coordinator asks only the shards owning these 9 cells. Here they cover all three
(`tdr1v2` → 0; `tdr1v6 tdr1vd tdr1v9 tdr1v8 tdr1vb` → 1; `tdr1vf tdr1v3 tdr1vc` → 2);
a search confined to one cell asks one shard.

**Claim the resource** (read version v, write `remaining - amount` with `expectedVersion: v`):

```bash
curl -X PUT "$C/v1/data/resource:tdr1v9:8a7c3e0e-4c1d-4b9a-9d55-0d3c2f1a9b77" -H 'Content-Type: application/json' -d '{
  "value": { "...": "same document, capacity.remaining 480, updatedAt now" },
  "indexes": { "collection": "resource", "type": "WATER", "status": "AVAILABLE", "geoCell": "tdr1v9" },
  "expectedVersion": 1 }'
# → 200 "version": 2.  A second claim with "expectedVersion": 1 → 409 (no double booking).
```

When `remaining` reaches 0, write `"status": "DEPLETED"` in **both** `value` and
`indexes`, so the resource stops appearing in candidate searches.

**Mark the request matched:** conditional write of the request with
`status: MATCHED`, `assignedResourceId: "res_tdr1v9_8a7c…"` in `value`,
`indexes.status: MATCHED`, and `expectedVersion` = the version just read.

**List** (`GET /resources?type=WATER&status=AVAILABLE`):
`POST /v1/query {"collection":"resource","match":{"type":"WATER","status":"AVAILABLE"}}`
(no `geoCells`, so all shards are asked).

**Move a resource:** create it under `resource:{newCell}:{uuid}` (new `resourceId`),
then delete the old key with `DELETE /v1/data/{oldKey}?expectedVersion=v`.

## 8. Responses to expect

| Status | `error` | When | Service action |
|---|---|---|---|
| `400` | `INVALID_REQUEST` | bad key shape, indexes contradict key, malformed body, unknown field | bug in the service: fix it |
| `404` | `NOT_FOUND` | no record (or it was deleted) | map to the public `404` |
| `409` | `VERSION_CONFLICT` | `expectedVersion` stale, or `0` and the key exists | re-read, decide again |
| `412` | `PRECONDITION_FAILED` | `expectedVersion ≥ 1` but the key does not exist | treat as not found |
| `503` | `STORAGE_UNAVAILABLE` | a shard has no live node; or the shard's primary was replaced during this write | **outcome unknown**: re-read, then retry |

Every error body: `{ "error": "...", "message": "...", "timestamp": "..." }`.
